# Changelog

## v4.4.0 — 2026-10-10

Nice-to-haves pass; fully backward compatible (same 17 tools — no new MCP tool this release — same REST routes, everything v3–v4.3 untouched):

- **`ghost-bridge doctor`** — a read-only diagnostic subcommand (`bin` target + `scripts/doctor.mjs`, in the spirit of Ghost Hands' doctor). Checks: Node version; version consistency across all 3 `package.json` files plus the `SERVER_VERSION` / `RELAY_VERSION` code constants; the context file (real vs EXAMPLE template, validity); relay reachability when `GHOST_RELAY_URL` / credentials are configured (`/health` + `/probe`, relay-vs-local version comparison, key acceptance + scope via harmless authed reads, offline-outbox pending count); and MCP config sanity with `--config <path>` (parses, carries a `ghost-bridge` entry, entry points at an existing `server.js`, wired to a relay or queue repo, no bridge key sitting in the config). Every check is PASS/WARN/FAIL/SKIP with a plain-language fix for anything that isn't a PASS. `--json` for machines. **Exit 1 only on FAIL.** Credentials are never printed — presence and scope only.
- **Task dependencies** — tasks gain `blockedBy: number[]` (REST create + PATCH, both MCP `ghost_handoff`s; `dependsOn` accepted as an alias). Every blocker must already exist — a dangling blocker is a **400** on REST and a "Not sent" over MCP — and a task can never block itself. Blocked state is **computed on every read**, never stored: a task is blocked while any blocker is not `done`/`cancelled`, and completing or cancelling a blocker unblocks its dependents automatically. **Documented decision:** an *archived* blocker counts as satisfied, because archive only ever takes done/cancelled tasks — an archived blocker is a finished blocker by construction. Blocked tasks carry `blocked` + `blockedByUnfinished` on reads, a `[BLOCKED by #n]` marker in `ghost_inbox`, an explanation line in `ghost_task_result`, and a ⛓ BLOCKED badge on the board. **Claiming a blocked task** (PATCH to `in-progress` or `{claim: true}`) is a **409** naming the unfinished blockers.
- **Digest** — `GET /api/digest?hours=24` (any authed key, readonly included) returns a structured summary: counts by status, tasks completed in the window (with `completedBy` recovered from the event log when available), the **waiting-on-owner** (`needs-approval`) list, the overdue list, the blocked list, new-notes/new-tasks counts for the window, and agents seen. `?format=md` renders the same digest as Markdown text for pasting into a chat or report. No new MCP tool: `ghost_bridge_status` gains a **Digest (24h)** section (the local client reads `/api/digest`; the hosted MCP computes it internally). The board shows a **dismissible digest banner** under the header with the waiting-on-owner + overdue counts whenever either is above zero (dismissing lasts until the counts change).
- **`/metrics`** — `GET /metrics`, unauthenticated like `/probe`, returns **counts only** in Prometheus text format: `ghost_bridge_tasks{status="…"}` gauges, `ghost_bridge_keys`, `ghost_bridge_events_total` (current log size), `ghost_bridge_overdue`, `ghost_bridge_archived`, and `ghost_bridge_version_info{version="4.4.0"} 1`. No titles, no key material, no event bodies — safe to scrape. The Netlify function's routed paths gain `/metrics` too.
- **Context history** — every `PUT /api/context` bumps a monotonically increasing context version (returned in the PUT response and as an **additive** `contextVersion` field on `GET /api/context` — existing consumers are unaffected) and archives the outgoing context as `context-history:<n>` with a timestamp. Retention is the **last 10 versions in total** (current + up to 9 snapshots); older snapshots are pruned. `GET /api/context/history` (readonly OK) lists versions — `n`, `at`, project count, current flagged — and `GET /api/context/history/<n>` returns that snapshot, current version included. Importing a backup restarts history at version 1 (snapshots are not carried over). The local MCP's `ghost_whoami` / `ghost_bridge_status` show the relay context version when the relay provides one.
- **Also fixed** — the hosted MCP's internal task-save rewrote the task index from the non-archived working set, which would have dropped archived tasks out of the index (and out of exports and dependency resolution) after any hosted write; it now merges with the stored index.
- Tests: MCP suite **122** checks (new Phase G v4.4 block — dependency handoffs/blocked markers/dangling refusal/alias/digest section against a real relay; new Phase H — doctor spawned via the real bin against a fixture relay: `--json` structure, exit 0 healthy, key-scope detection, valid/broken `--config`, FAIL exits 1, key never printed), relay suite **192** checks (dependency validation/claim-409/unblock-on-done/cancel/archived-blocker fixture/hosted markers, digest JSON + Markdown + readonly + completedBy, /metrics format + no-leak, context history 3-PUT versions + snapshot retrieval + 11th-PUT prune + readonly reads, board badge/banner statics). Demo and pack audit unchanged in shape and passing.

## v4.3.0 — 2026-10-10

Coordination + scale pass; fully backward compatible (same 17 tools, same REST routes, scopes/leases/idempotency/signed webhooks/export/outbox from v4.1–v4.2 untouched):

- **Capsule concurrency (optimistic revisions)** — relay files gain a revision counter (stored under `filerev:<path>`; import resets imported files to rev 1). `GET /api/files` returns `{path, text, rev}` plus an `ETag: "rev-<n>"` header. `PUT /api/files` accepts an optional `expectedRev`: a mismatch returns **409** `{error (with a plain-language merge hint), currentRev, path}` and writes nothing; a non-numeric `expectedRev` is a 400. Without `expectedRev`, writes stay last-write-wins (v4.2 behavior — old scripts keep working). Files written before v4.3 (no stored rev) read as rev 1, and their first v4.3 write lands at rev 2. `ghost_capsule_update` now passes the rev it read automatically in **both** the local MCP and the hosted MCP (the hosted MCP switched capsule access to targeted, rev-aware store reads/writes), and a collision returns a clear "was NOT updated — revision conflict … re-read and merge" result instead of a silent clobber.
- **Agent presence** — `POST /api/presence {displayName?, capabilities?: string[], status?: "online"|"busy"|"away"}` (400 on an unknown status or non-array capabilities) stores a presence record under the caller's **key name**; `GET /api/presence` returns `{agents, windowMinutes}` for agents seen within `GHOST_BRIDGE_PRESENCE_MINUTES` (default 10) — name, displayName, capabilities, status, lastSeen; never hashes or key material. Deliberate scope call: presence is a read-ish surface (a heartbeat only ever writes the caller's own record), so **readonly keys may heartbeat and read presence**; every other write stays full-only. The local MCP sends a heartbeat automatically on `ghost_bridge_status` and `ghost_handoff` (throttled to one per 30 s per process, best-effort — it can never fail the tool), and `ghost_bridge_status` (local + hosted) lists the online agents. The board grows an **Agents strip** with freshness dots (green < 2 min, amber inside the window), refreshed on events and every 30 s.
- **Task scheduling** — tasks gain optional `dueAt` / `notBefore` (ISO strings; REST create + PATCH also accept the `due` / `schedule` aliases; `ghost_handoff` local + hosted takes `due` / `schedule` arguments; offline-outbox entries carry them through the flush). Malformed dates are a **400** with a clear error on REST, and a pre-flight "Not sent" error in both handoff tools (nothing is filed). Flags are computed on every read, never stored: `overdue` = queued and past `dueAt`; `scheduled` = queued and `notBefore` in the future. Both ride along on task reads (`publicTask`), `ghost_inbox` lines (`[OVERDUE]` / `[scheduled — not before …]`), `ghost_task_result`, and the board (red OVERDUE badge, amber scheduled badge + due/not-before meta, detail-drawer lines). `/health` gains an `overdue` count. `PATCH /api/tasks/:id` accepts schedule-only patches (set or clear with `null`) that never touch status or an active claim lease, and schedule fields may ride along with any other patch. **No timer service**: events still fire at creation; the skip rule is carried where pickup workers see it — the `work_like_mrghosty` prompt (local + hosted) and every scheduled handoff's result text say to skip not-yet-due tasks.
- **Pagination + search at scale** — `GET /api/tasks` accepts `limit`/`offset` (default limit 50, max 200 — unchanged for callers who pass nothing) and now adds `total`/`limit`/`offset` to the response **only when a paging param is used**, so the default response shape is byte-for-byte the v4.2 one. New `q=` filter: any-word match over title + body + comments, the same semantics as `ghost_search_tasks`. Hosted `ghost_inbox` and local `ghost_inbox` gain an `offset` argument (the local GitHub-queue transport pages by fetching `limit + offset` and slicing). Tests prove 15 tasks page 5/5/5 with no dupes or gaps, newest-first, and that `q=` finds a word that appears only in a comment.
- **Archive + retention** — `POST /api/tasks/archive` (**full-scope only**; readonly gets 403 from the scope gate) archives eligible tasks — `done`/`cancelled` with `closedAt || updatedAt` older than the cutoff — by flagging them in place (`archived`, `archivedAt`); a `tasks.archived` event fires when anything moves. The cutoff is the request body's `days` when given, else `GHOST_BRIDGE_ARCHIVE_DAYS` (default 30); `days: 0` is a documented no-op with an explanatory note; a non-numeric `days` is a 400. **Explicit calls only — no automatic/timer archiving, ever.** Archived tasks are excluded from default task lists, the board, `/api/meta`, and `/probe` counts; they remain in `GET /api/export` (backups lose nothing), readable via `GET /api/tasks?archived=1` and `GET /api/tasks/:id`, and `ghost_search_tasks` (local + hosted) searches them too, always marked `[archived]`. `/health` reports an `archived` count and excludes archived tasks from `tasks`/`byStatus`. CLI wrapper: `ghost-bridge archive [--days N]` (`scripts/archive.mjs`).
- **Also fixed** — the local `ghost_search_tasks` refused to run at all on relay-only configurations (its guard demanded the GitHub queue config even when the relay transport was configured); it now matches the other tools' guard, which is what makes archived search reachable without a GitHub queue.
- Tests: MCP suite **107** checks (presence heartbeat + agent list against the Phase D stub; new Phase G against a real relay — capsule rev lifecycle 1→2 via the tools, scheduled/overdue handoffs with stored fields + flags + result wording, malformed-due rejection filing nothing, inbox 5/5 paging over 15 tasks disjoint, archived task found + marked by search and excluded from inbox; new Phase G2 proving a 409 surfaces "NOT updated … rev 7 / rev 5" instead of a clobber), relay suite **156** checks (file rev lifecycle incl. legacy-file rev 1→2, presence window incl. a 120-minute env widening, readonly heartbeat/read allowed, scheduling create/PATCH/clear + hosted wording + health count, pagination integrity + `total` shape rules, archive eligibility/exclusion/export/readonly-403/disabled-by-days-0 + env-0, board agents/badges statics). Demo and pack audit unchanged in shape and passing.

## v4.2.0 — 2026-10-10

Trust + portability pass; fully backward compatible (same 17 tools, same REST routes, scopes/leases/idempotency from v4.1 untouched):

- **Signed webhooks** — when `GHOST_BRIDGE_WEBHOOK_SECRET` is set on the relay, outbound webhook POSTs carry `x-ghost-event: <type>` and `x-ghost-signature: sha256=<hmac-sha256 hex of the raw body>`. Ships with `scripts/webhook-verify.mjs` (a timing-safe `verifyGhostSignature(rawBody, header, secret)`) and `scripts/webhook-receiver.mjs`, a complete verified receiver example. With no secret set, deliveries remain unsigned, exactly as in v4/v4.1. `docs/events.md` now documents verification instead of the old "events are unsigned" caveat.
- **Backup / restore** — `GET /api/export` (full-scope key only; readonly gets 403) returns one JSON document: `{format, version, exportedAt, keys (names + scopes + sha256 hashes only — plaintext keys never exist server-side), tasks (complete, including comments, attachments, and the internal idemKey), files, context, counter}`, with the event log included on `?events=1`. `POST /api/import` (full-scope only) restores into an **empty** relay; a non-empty relay is refused with 409 unless `?force=true` **and** `{"confirm": "OVERWRITE"}`. Imported keys replace the key list, but the importing key is preserved (renamed `<name>-preimport` on a name collision) so a restore can't lock the operator out. CLI wrappers: `ghost-bridge backup [--out f] [--events] [--stdout]` and `ghost-bridge restore <file> [--force]` (`scripts/backup.mjs` / `scripts/restore.mjs`). Proven by a full round-trip test: build state → export → fresh relay → import → same tasks/files/context, imported keys authenticate, readonly stays readonly.
- **Board task detail + owner actions** — the relay board (`relay/public/index.html`) now opens a detail drawer on any task click: full thread (comments + structured results), attachments list, and lease state, refreshed live. With a full-scope key the owner can **reply** (existing comment endpoint), **approve** a `needs-approval` task (comment + status back to queued — the exact `ghost_reply` REST semantics, no parallel path), and **cancel** (comment + cancelled). Read-only keys see the full thread view-only with the action area replaced by an explanation of the scope. Still a single static file, no build, no external assets.
- **MCP offline outbox** — in `mcp/server.js`, a relay-transport `ghost_handoff` that hits a *transport* failure (the relay is unreachable; fetch never got an HTTP response) is saved to `GHOST_OUTBOX_PATH` (default `~/.ghost-bridge/outbox.json`, mode 0600) with title/body/project/priority/attachments and an idempotency key minted at queue time; the tool result says clearly that it was QUEUED, not delivered. `ghost_bridge_status` and later `ghost_handoff` calls flush the outbox in order once the relay answers; delivery is exactly-once via the stored idempotency key, and status reports the pending count + last flush result. Relay HTTP error responses (4xx/5xx) are never queued. GitHub and local-file transports unchanged.
- **Packaging proof** — the root package gains a `files` allowlist (with negations that keep `context.json` / `.setup-secret` / `.netlify` out — npm's `files` field otherwise overrides `.gitignore` inside included directories, which the audit now guards against permanently). `scripts/pack-audit.mjs` (`npm run pack-audit`, wired into CI) runs `npm pack`, unpacks the tarball, and asserts: zero private-data markers, no secret/state files packed, and the runtime essentials present. CI also gains a Node **18/20/22** matrix for both suites.
- Tests: MCP suite 88 checks (new offline-outbox phase against a dead-then-real relay), relay suite 104 checks (signed webhooks + verify helper, export/import round-trip incl. readonly rejection and force/confirm rules, board drawer static checks). Demo unchanged and passing; pack audit passing (46 files).

## v4.1.0 — 2026-10-10

Hardening + usability pass on the v4 platform; fully backward compatible (same 17 tools, same REST routes, migrated `primary` keys untouched):

- **Scoped keys** — every key now has a scope: `full` (default; everything) or `readonly` (reads only: task list/read, files list/get, context get, board, events, and the read-only MCP tools). A readonly key attempting a write — REST or hosted MCP — gets a clear 403/`isError` explanation, never a silent success; it cannot mint, list, or revoke keys. `POST /setup` and `POST /api/keys` accept `scope`; `GET /api/keys` shows it. Legacy keys are `full`.
- **Claim leases** — moving a task to `in-progress` (or `PATCH {claim: true}`) claims it for the caller's key: `claimedBy` + `claimExpiresAt` (default 15 min, `GHOST_BRIDGE_CLAIM_MINUTES`; per-claim override via `claimMinutes`). A second key claiming an actively leased task gets **409** naming the holder and expiry; expired leases can be re-claimed; the holder re-claiming renews; leaving `in-progress` (release to queued, done, cancelled, needs-approval) clears the lease. `ghost_task_result` surfaces the holder. Two agents can no longer silently double-work one task.
- **Idempotent handoffs** — `ghost_handoff` (local MCP relay transport + hosted MCP) and `POST /api/tasks` accept an optional `idempotencyKey`. Re-filing the same key from the same bridge key returns the existing task (`200` + `duplicateSuppressed` on REST, a "Duplicate suppressed" note over MCP) instead of a second task. The key is stored on the task and stripped from normal reads. The duplicate-title guard is unchanged for keyless handoffs.
- **Live board UI** — the relay board page is now a real v4 board: live updates over the events long-poll (periodic-refresh fallback), Queued / Working / Waiting on owner / Done columns, claim holder + live lease countdown in Working, 📎 attachment indicators, structured-result summaries, and a keys panel (scope badges, last-used, mint + revoke) shown only to full-scope keys. Still one static file, no build step, no external assets.
- **Relay self-protection + observability** — per-key rate limiting (`GHOST_BRIDGE_RATE_PER_MIN`, default 600/min/key) returns **429 + Retry-After** when exceeded; `/probe` + `/health` share a light unauthenticated bucket. The event log is capped (`GHOST_BRIDGE_EVENT_CAP`, default 500). `/health` now also reports task counts by status, the number of keys, and the event-log size — counts only, never key material.
- Tests: MCP suite 78 checks, relay suite 80 checks (new coverage for scopes on REST + MCP, lease conflict/expiry/release/done, idempotent re-handoff on REST + hosted MCP + local client, rate-limit trip on a dedicated low-limit instance, and event-cap trimming). Demo unchanged and passing.

## v4.0.0 — 2026-10-10

The "shoot for the moon" release. Public-repo foundation, and the bridge grows from a single-client queue into a small multi-agent platform:

- **Unified public repo** — MCP server, relay, CLI, docs, and tests in one tree; root `README.md`, `CONTRIBUTING.md`, `SECURITY.md`, GitHub Actions CI running both suites plus a private-data scan on every push.
- **Multi-client keys** — named keys per machine/client stored as sha256 hashes with `createdAt`/`lastUsedAt`; `POST /api/keys` (mint, optionally server-generated, shown once), `GET /api/keys` (names + timestamps only), `DELETE /api/keys/:name` (revoke one without touching the others). Legacy v3 `{keyHash}` configs auto-migrate to a named key called `primary` on first boot — existing clients keep working with no re-setup.
- **Push wake** — append-only event log (`task.created`, `task.comment`, `task.status`, `key.registered`, `key.revoked`); `GET /api/events?since=<seq|ISO>&wait=<sec>` long-poll (serverless-safe), `GET /api/events/stream` SSE on local/Docker servers, optional outbound webhook via `GHOST_BRIDGE_WEBHOOK_URL` (best-effort, 3 s timeout, failures never break a request). Polling untouched.
- **Attachments + structured results** — `ghost_handoff` (local MCP and hosted MCP) and `POST /api/tasks` accept `attachments[]` (`path` to a relay file, or inline `dataBase64` ≤ 256 KB decoded, ≤ 5 per task). Comments and task PATCHes can carry `result: {status, summary, files[]}`; `ghost_task_result` surfaces attachments and structured results. Text-only tasks are fully backward compatible.
- **One-command install** — root package `ghost-bridge` with a bin CLI: `npx ghost-bridge setup|server|relay|demo|watch`. `node mcp/setup.mjs` still works exactly as before.
- **Clients** — verified-format MCP config examples + setup notes for Antigravity, Cursor, Claude Code, and Codex (`docs/clients/`).
- **Self-host** — Dockerfile + docker-compose (volume-backed store via `GHOST_BRIDGE_STORE_FILE`), Netlify deploy button, relay `/health` now returns version + queue counts.
- **Demo** — `scripts/demo.mjs` boots a local relay and proves multi-key auth, hosted-MCP handoff with an attachment, the event log, and a structured result end-to-end.
- **Privacy** — the public tree ships `context.example.json` only. Test suites re-fixtured to self-created fixture data; MCP suite 75/75, relay suite 49/49.
- Versions: MCP server and relay both report `4.0.0`.
